# 酒店产品子模型体系 — 模块化设计 v3.0

> 核心理念：6维度分析模型为通用底座，5大产品子模型为可选模块。酒店按需开通，AI自动适配。
> 基于：五步法 + 陶总五大反对 + 禁用词语表 + 智能体三句话法
> 版本：v3.0（子模型化重构）

---

**设计原则**：
1. **底座通用**：6维度分析模型 + 三大引擎（客户分析/匹配规则/自然语言输出），所有酒店必开，不可关闭
2. **子模型可选**：5大产品子模型按需开通，酒店缺哪个开哪个，不需要的不开
3. **映射灵活**：每个子模型与酒店实际房型多对多映射，不是一对一绑定
4. **输出统一**：无论开通多少子模型，AI对客输出统一为自然语言产品描述，客户无感知"子模型"

## 二、通用底座详解（必开，所有酒店共用）

### 2.1 6维度分析模型（核心底座）

底座保留v2.0的6维度分析框架，但去掉了具体产品命名，只保留分析维度本身。

| 维度 | 子项 | 数据类型 | 说明 |
|------|------|----------|------|
| **硬件设施** | 面积/床型/睡眠品质/景观/卫浴/特殊设施 | 数值/枚举/布尔 | 客房的物理属性，与酒店实际房型一一对应 |
| **空间位置** | 城市区位/交通便利性/周边配套/朝向/楼层/噪声 | 枚举 | 客房的位置属性，影响出行适配度 |
| **服务范围** | 服务响应/专属空间/早餐等级/礼遇/特殊服务/预判 | 枚举/布尔 | 酒店可交付的服务承诺 |
| **价格定位** | 价格区间/性价比/动态定价/附加费用/成本结构 | 数值/枚举 | 产品的价格属性 |
| **风格特征** | 调性风格/客群画像/标准化程度/情绪价值 | 枚举 | 产品的情感属性 |
| **客群适配** | 主要客群/出行目的/时长适配/安静倾向 | 枚举/多选 | 产品与客群的匹配关系 |

> **底座设计原则**：6维度只分析"这间房是什么"，不判断"这间房属于哪个产品类型"。产品类型由子模型定义。

### 2.2 三大引擎（必开，与底座绑定）

| 引擎 | 功能 | 输入 | 输出 |
|------|------|------|------|
| **客户分析引擎** | 解析客户输入，提取结构化特征 | 客户自然语言输入或系统数据 | 6维度特征向量（每项0-100分） |
| **匹配规则引擎** | 计算客户与酒店实际房型的匹配度 | 客户特征向量 + 酒店实际房型6维度数据 | 每房型的匹配规则判定结果（匹配/部分匹配/不匹配）+ 规则命中明细 |
| **自然语言输出引擎** | 将匹配结果转化为对客描述 | 匹配结果 + 酒店房型的具体属性 | 自然语言产品描述（客户视角） |

> **引擎设计原则**：引擎是通用能力，与酒店品牌、定位无关。无论经济型还是奢华型，引擎逻辑相同。

### 2.3 客户分析三维度（核心输入规范）

客户分析引擎从客户输入中提取三个核心维度，转化为6维度特征向量：

| 维度 | 说明 | 提取方式 | 示例 |
|------|------|----------|------|
| **客户身份阶层** | 客户的身份定位和社会层级 | 从职业、会员等级、企业协议、历史消费推断 | 企业高管/中产家庭/学生/背包客 |
| **消费能力梯次** | 客户的预算区间和价格敏感度 | 从明确预算、历史消费、身份阶层推断 | 经济敏感/品质追求/体验优先/预算无上限 |
| **出行目的** | 客户本次出行的核心诉求 | 从客户直接陈述或行为数据推断 | 商务出差/中转过夜/休闲度假/家庭出游/纪念日/长住 |

> **三维度→6维度映射**：客户分析引擎将上述三个核心维度，映射为6维度特征向量中的"客群适配""价格定位"等子项，供匹配规则引擎使用。

## 三、五大产品子模型（可选，按需开通）

### 3.1 子模型设计规范（每个子模型统一结构）

每个子模型包含以下模块：

```
子模型 = {
  "子模型ID": "transit_stay",
  "子模型名称": "中转房",
  "开通条件": "酒店有至少1种房型满足面积15-22㎡、基础卫浴、无专属服务",
  "产品定义": { ... },        ← 产品标准定义（6维度阈值）
  "服务标准": { ... },        ← 对客服务标准（前台/客房/经营者）
  "AI能力": { ... },          ← 开通后AI新增的能力
  "房型映射规则": { ... },    ← 与酒店实际房型的映射逻辑
  "自然语言模板": { ... },    ← 对客输出的描述模板
  "适用酒店类型": [ ... ]     ← 哪些酒店适合开通
}
```

### 3.2 子模型A：中转房（基础模块，默认开通）

#### 3.2.1 产品定义（6维度阈值）

| 维度 | 阈值 | 说明 |
|------|------|------|
| 硬件设施 | 面积15-22㎡ / 基础床型 / 经济床品 / 无窗或内景 / 标准淋浴 | 满足底线即可 |
| 空间位置 | 交通枢纽/商务区边缘/居民区 | 不苛求核心区 |
| 服务范围 | 自助为主 / 无专属空间 / 无或简餐 / 无礼遇 | 服务极简 |
| 价格定位 | 一线150-350元 / 新一线100-280元 / 二线80-220元 | 成本极限控制 |
| 风格特征 | 简洁实用 / 无情绪价值 | 无设计感 |
| 客群适配 | 单人/中转/过夜/预算敏感 | 不追求复购 |

#### 3.2.2 服务标准

| 角色 | 服务标准 | 动作要求 |
|------|----------|----------|
| 前台 | 快速办理（3分钟内），无额外介绍 | 识别中转客户，不推销升级 |
| 客房 | 干净、安全、热水稳定 | 底线检查，不做夜床 |
| 经营者 | 可预期性管理，每家店标准一致 | 不接受个性化要求 |

#### 3.2.3 AI能力（开通后）

| 能力 | 说明 | 触发条件 |
|------|------|----------|
| 中转识别 | 自动识别"中转/过夜/凌晨到达"客户 | 客户分析含"中转"或入住时间<6小时 |
| 快速推荐 | 直接推荐最低价格房型，不展示其他选项 | 预算<350元 + 停留<1晚 |
| 底线承诺 | 输出"干净、安全、热水稳定"，不承诺其他 | 所有中转房推荐 |

#### 3.2.4 房型映射规则

```
映射逻辑：
IF 酒店实际房型.面积 <= 22㎡ 
   AND 酒店实际房型.床品 = "经济型" 
   AND 酒店实际房型.服务 = "基础" 
THEN 映射为"中转房" 
   ELSE 不映射
```

> **多对多映射**：一间酒店可能有多个房型映射到中转房（如大床/双床/无窗），也可能没有房型映射到中转房（如纯中端酒店）。

#### 3.2.5 自然语言模板

```
【中转房】— {price}元/晚

- 房间{area}㎡，{bed_type}，干净卫浴，热水稳定
- {location}，{transport}，{包含/不包含}送机班车
- {price}元含服务费，无额外费用，早餐可选加{breakfast_price}元
- 对标汉庭、锦江之星的清洁和安检标准

【为什么匹配】：
{客户中转原因}，只需要睡觉+安全，不需要为景观和豪华设施付费。
```

#### 3.2.6 适用酒店类型

- 经济型酒店（汉庭、锦江之星、7天、如家）
- 中端酒店的基础房型（全季/亚朵的最低配房型）
- 机场/高铁站附近的所有酒店
- 任何酒店只要有面积<22㎡、基础配置的房型即可开通

### 3.3 子模型B：休旅房（可选模块）

#### 3.3.1 产品定义（6维度阈值）

| 维度 | 阈值 | 说明 |
|------|------|------|
| 硬件设施 | 面积22-30㎡ / 加大床 / 中高端床品（普兰特/金可儿级别）/ 标准窗景 | 睡眠品质为核心 |
| 空间位置 | 商务区核心/景区入口/商业综合体周边 | 便利优先 |
| 服务范围 | 标准服务 / 延迟退房至14:00 / 自助早餐 | 服务标准但不专属 |
| 价格定位 | 一线350-600元 / 新一线280-500元 / 二线220-400元 | 性价比最优区间 |
| 风格特征 | 生活方式/人文/属地特色 | 情绪价值来源 |
| 客群适配 | 双人/家庭/休闲/标准商旅 | 最广泛客群 |

#### 3.3.2 服务标准

| 角色 | 服务标准 | 动作要求 |
|------|----------|----------|
| 前台 | 强调床垫品牌和属地早餐特色 | 主动介绍睡眠品质 |
| 客房 | 确保床品完好、安静朝向 | 睡眠品质是核心交付 |
| 经营者 | 属地人文更新（摄影/书籍/早餐） | 每季度更新属地内容 |

#### 3.3.3 AI能力（开通后）

| 能力 | 说明 | 触发条件 |
|------|------|----------|
| 睡眠品质推荐 | 自动强调床垫品牌、床品参数 | 客户分析含"睡眠敏感"或"品质敏感" |
| 属地介绍 | 输出酒店所在城市的属地特色 | 客户分析含"休闲"或"首次到访" |
| 性价比计算 | 横向对比同级酒店，展示性价比优势 | 客户预算在300-600元区间 |

#### 3.3.4 房型映射规则

```
映射逻辑：
IF 酒店实际房型.面积 22-30㎡ 
   AND 酒店实际房型.床品 = "中高端" 
   AND 酒店实际房型.早餐 = "自助" 
   AND 酒店实际房型.价格 >= 350元 
THEN 映射为"休旅房" 
   ELSE 不映射
```

#### 3.3.5 自然语言模板

```
【休旅房】— {price}元/晚，含早餐和WiFi

- {area}㎡，{bed_brand}级别床垫，{bed_type}，{thread_count}支长绒棉床品
- 卫浴有淋浴{包含/不包含}浴缸可选
- {location}，{transport}，{distance_to_attraction}
- 自助早餐，含{local_breakfast_item}+现磨咖啡
- 延迟退房至14:00

【为什么匹配】：
{客户出行目的}，核心需求是睡眠品质+便利，{price}元预算花在床垫和早餐上，不花在对周末无用的商务设施上。
```

#### 3.3.6 适用酒店类型

- 中端酒店（亚朵、全季、桔子、维也纳、麗枫）
- 高端酒店的基础房型（万豪万怡、希尔顿花园、福朋喜来登）
- 精品民宿/客栈（面积够、床品达标、有属地特色）
- 任何酒店只要有面积22-30㎡、中高端床品、含早餐的房型即可开通

```
【为什么匹配】：
出差时间紧，房间=临时办公室，硬件设施和服务范围围绕"省时间"设计，不需要为景观和休闲设施付费。
```

#### 3.4.6 适用酒店类型

- 商务型酒店（万豪、希尔顿、喜来登、威斯汀）

- 高端酒店的标准商务房型（行政楼层/行政房）

| 管家预联系 | 提醒前台/管家提前联系确认需求 | 匹配度假房 |

#### 3.5.4 房型映射规则

```
映射逻辑：
IF 酒店实际房型.面积 >= 35㎡

   AND 酒店实际房型.管家 = true 
THEN 映射为"度假房" 
   ELSE 不映射
```

## 五、子模型开通与映射流程

### 5.1 开通流程（酒店接入时）

```
Step 1: 酒店提交房型清单
  └─ 每房型的：面积/床型/床品/景观/卫浴/服务/早餐/价格/位置

Step 2: 系统自动映射
  └─ 通用底座读取房型数据
  └─ 每个子模型执行映射规则
  └─ 输出：该酒店可开通的子模型列表 + 映射关系

Step 3: 酒店确认开通
  └─ 酒店选择开通哪些子模型（默认必开中转房，其他自选）
  └─ 酒店可微调映射关系（如"我家大床房A映射到休旅房而非中转房"）
  └─ 酒店确认后生效

Step 4: AI能力激活
  └─ 已开通子模型的AI能力自动激活
  └─ 未开通子模型的AI能力不激活（不输出对应产品类型）
```

### 5.2 映射灵活性设计

| 灵活性 | 说明 | 示例 |
|--------|------|------|
| **多对多映射** | 一个房型可映射到多个子模型 | 万豪行政套房 → 可映射商旅房（商务客户）或度假房（休闲客户） |
| **一对多映射** | 一个子模型可映射到多个房型 | 休旅房 → 可映射高级大床房、高级双床房、几木大床房 |
| **零映射** | 子模型可映射到0个房型 | 纯经济型酒店 → 休旅房映射数为0，不输出休旅房 |
| **人工微调** | 酒店可人工覆盖自动映射 | 酒店认为"我家大床房A虽然面积25㎡，但床品普通，应映射中转房而非休旅房" |

## 六、AI对客输出统一性

### 6.1 输出统一原则

无论酒店开通多少子模型，客户视角的体验统一：

| 方面 | 统一要求 | 原因 |
|------|----------|------|
| **产品命名** | 统一使用5类创新命名（中转房/休旅房/商旅房/度假房/长住房） | 客户不感知酒店品牌差异，只感知产品类型 |
| **描述风格** | 统一自然语言输出，客户视角第一 | 不因酒店品牌改变描述风格 |
| **匹配逻辑** | 统一6维度匹配规则，不因酒店改变规则标准 | 同一客户在不同酒店得到一致的评价逻辑 |
| **服务预判** | 统一角色分工（前台/客房/经营者） | 不因酒店改变服务标准描述 |

### 6.2 输出示例（同一客户在不同酒店）

**客户分析**：预算800元，商务出差，单人，安静+办公需求

**在汉庭（开通了中转房+休旅房）**：
```
【休旅房】— 498元/晚，含早餐和WiFi

- 25㎡，加大床，品牌床品
- 独立卫浴，安静朝向
- 商务区附近，地铁直达
- 自助早餐，含属地特色

【为什么匹配】：
商务出差核心需求是睡眠品质+便利，500元预算花在床垫和早餐上。汉庭无行政酒廊和办公区，但休旅房满足底线商务需求。
```

**在亚朵（开通了休旅房+商旅房）**：
```
【商旅房】— 798元/晚，含行政酒廊和早餐

- 30㎡，独立办公区（1.2米书桌、人体工学椅）
- 加大床，遮光帘+降噪，安静朝向
- 行政酒廊，晚上可处理邮件
- 快速入住通道，早餐可打包

【为什么匹配】：
出差时间紧，房间=临时办公室，商旅房围绕"省时间"设计。
```

**在万豪（开通了商旅房+度假房+长住房）**：
```
【商旅房】— 850元/晚，含行政酒廊和早餐

- 35㎡，独立办公区+人体工学椅
- 加大床，助眠配置
- 28楼行政酒廊
- 快速入住，早餐可打包
- 已按您的枕头偏好提前布置

【为什么匹配】：
出差时间紧，商旅房效率最优。万豪行政楼层商务设施完善，积分可累计。
```

> **核心观察**：同一客户在不同酒店得到的产品类型不同（汉庭→休旅房，亚朵/万豪→商旅房），但描述风格统一、匹配逻辑一致、客户体验连续。

## 七、扩展子模型设计（自定义能力）

### 7.1 为什么需要扩展子模型

5大子模型覆盖主流需求，但存在以下空白：
- **电竞酒店**：需要"电竞房"子模型（床+电竞设备+社交）
- **亲子酒店**：需要"亲子房"子模型（家庭设施+儿童服务+安全）
- **宠物友好酒店**：需要"宠物房"子模型（宠物设施+清洁标准）
- **长租房/公寓**：需要"公寓房"子模型（厨房+洗衣机+月租）
- **主题酒店**：需要"主题房"子模型（IP/设计/沉浸式）

```yaml

    - 网络: 有线千兆/无线WiFi6/专线
    - 电竞椅: 人体工学电竞椅级别
  社交属性:
    - 房间数: 单人间/双人间/五人间（开黑房）
    - 共享空间: 无/客厅/电竞大厅

  硬件设施: 面积22-35㎡ / 加大床 / 中高端床品 / 电竞设备（RTX4060+27寸144Hz+千兆）
  空间位置: 商务区/大学城/电竞馆附近
  服务范围: 标准服务 / 延迟退房至16:00 / 夜宵服务

    触发: 出行人数>=2 AND 客户分析含"团队/朋友"
  - 赛事联动: 推荐酒店周边的电竞赛事或活动
    触发: 客户入住期间有电竞赛事

房型映射规则:
  IF 酒店实际房型.电竞设备 = true 
     AND 酒店实际房型.网络 >= "千兆" 
  THEN 映射为"电竞房"

适用酒店类型:
  - 电竞主题酒店
  - 电竞酒店（如雷神电竞酒店、宜博电竞酒店）
  - 部分网咖转型酒店
  - 任何酒店只要配备电竞设备即可开通
```

## 九、实施路径

### 9.1 第一阶段：底座上线（1-2周）

- 部署6维度分析模型
- 部署三大引擎（客户分析/匹配规则/自然语言输出）
- 所有酒店默认开通底座
- 必开子模型：中转房（自动映射，无房型则标记"未激活"）

### 9.2 第二阶段：子模型开通（2-4周）

- 酒店提交房型清单
- 系统自动执行映射规则
- 酒店确认开通哪些子模型
- 激活已开通子模型的AI能力

### 9.3 第三阶段：扩展子模型（持续）

- 收集酒店自定义需求
- 按扩展子模型规范设计新子模型
- 标杆验证（找行业标杆拆解）
- 上线并开放给符合条件的酒店开通

## 十、交叉验证（三视角审视）

交叉验证不从"自检清单"出发，而是让三个利益相关方分别审视模型，提出真实质疑，只有三方都认为合理，模型才通过。

---

### 10.1 客户视角 — "这个推荐对我有用吗？"

| 审视问题 | 客户真实质疑 | 模型回应 | 验证结果 |
|----------|-------------|----------|----------|
| **推荐是否精准？** | "我预算500元，为什么要给我推荐800元的商旅房？" | 6维度匹配规则按阈值过滤，价格不匹配直接排除，不会出现超预算推荐 | ✅ 通过 |
| **描述是否听得懂？** | "休旅房是什么？和标准房有什么区别？" | 自然语言输出用"为什么匹配"段落解释，不提"子模型"概念，只说客户能得到什么 | ✅ 通过 |
| **不同酒店体验是否一致？** | "在汉庭和万豪，我都说要商务出差，推荐为什么不一样？" | 产品命名统一（中转房/休旅房/商旅房/度假房/长住房），匹配逻辑一致，但酒店硬件不同导致推荐房型不同，这正是"同一客户、不同酒店、各得其所" | ✅ 通过 |
| **是否有隐藏费用？** | "198元是否包含早餐和服务费？" | 中转房模板明确"198元含服务费，无额外费用，早餐可选加15元"，附加费用透明度在6维度中 | ✅ 通过 |
| **特殊需求是否被照顾？** | "我带孩子，需要安静，这个推荐有没有考虑？" | 客户分析三维度（身份/消费/目的）→6维度特征向量，安静倾向在"客群适配"和"硬件设施"中双重校验 | ✅ 通过 |

**客户视角结论**：客户看到的不是抽象模型，而是"为什么这个房适合我"的自然语言解释。推荐精准、描述具体、无套路、无隐藏费用。✅ 通过

---

### 10.2 酒店经营者视角 — "这个模型能帮我卖更多房吗？"

| 审视问题 | 经营者真实质疑 | 模型回应 | 验证结果 |
|----------|-------------|----------|----------|
| **开通是否灵活？** | "我只有30间房，没有行政酒廊，能不开商旅房吗？" | 子模型按需开通，无对应硬件则映射数为0，不强制开通，不输出不存在的产品 | ✅ 通过 |
| **映射能否微调？** | "我的大床房A虽然25㎡，但床品普通，不想叫它休旅房" | 酒店可人工覆盖自动映射，自动映射是建议，最终确认权在酒店经营者 | ✅ 通过 |
| **是否帮我升级销售？** | "客户预算500元，能否推荐600元的休旅房？" | 模型不主动超预算推荐，但可在"同级替代"中展示价格略高的选项，由客户自主选择。不套路、不强制 | ✅ 通过 |
| **数据能否回流？** | "我想知道本周商旅房预订量为什么下降" | 经营者视角数据看板：子模型预订趋势、客户分析分布、映射命中率、未匹配原因，驱动产品迭代 | ✅ 通过 |
| **是否增加运营成本？** | "休旅房要求属地早餐，我没法每季度更新" | 服务标准是最优实践建议，不是强制要求。酒店可执行"基础版"（标准自助早餐）而非"完整版"（属地特色），模型自适应 | ✅ 通过 |

**经营者视角结论**：模型不强制酒店做超出能力的事，而是"有什么卖什么、叫什么是什么"，同时提供数据洞察帮助迭代。✅ 通过

---

### 10.3 酒店同业竞争者视角 — "这个模型有竞争优势吗？"

| 审视问题 | 竞争者真实质疑 | 模型回应 | 验证结果 |
|----------|-------------|----------|----------|
| **产品命名是否可抄袭？** | "中转房/休旅房/商旅房，对手也能抄" | 命名可抄，但6维度阈值、映射规则、标杆出处、自然语言模板是组合壁垒，且酒店实际房型数据是私有资产，对手无法复制同一家酒店的映射关系 | ✅ 通过 |
| **是否帮助酒店差异化？** | "全酒店都用同一套模型，我怎么和别人不一样？" | 底座通用，但子模型开通组合、映射关系、服务标准执行深度、属地内容更新频率，每家酒店不同，正是差异化空间。模型是框架，填充什么是酒店自己的事 | ✅ 通过 |
| **是否降低价格竞争？** | "模型让客人只看价格，怎么办？" | 6维度匹配规则中，"价格定位"只是维度之一，"睡眠品质""情绪价值""服务预判"同等权重，引导客户从"比价格"转向"比适合" | ✅ 通过 |
| **是否保护酒店利润？** | "客户分析逼着我降价的吗？" | 客户分析三维度（身份/消费/目的）不暴露客户隐私，只用于匹配。模型不压价，而是帮酒店找到"愿意为这个体验付这个价格"的客户 | ✅ 通过 |
| **扩展子模型是否形成生态壁垒？** | "电竞房/亲子房，谁先定义谁受益？" | 扩展子模型设计规范已公开，但标杆拆解（哪家电竞酒店？）和实际数据（显卡型号、赛事联动）需要时间积累，先行者定义标准，后来者跟随 | ✅ 通过 |

**竞争者视角结论**：模型框架可学习，但映射关系、服务执行、数据积累、标杆拆解形成复合壁垒。模型的目标是帮酒店从"价格竞争"转向"匹配竞争"。✅ 通过

### 10.4 三视角综合结论

| 视角 | 核心关切 | 验证结果 |
|------|----------|----------|
| **客户视角** | 推荐精准、描述具体、无套路、无隐藏费用 | ✅ 通过 |

**综合结论**：三视角均通过，模型可进入下一阶段（酒店接入试点）。
