## 第一层：核心大模型底座（最内圈）

### 1.1 企业自动驾驶大模型

**定位**：公司级核心关系网络与公共能力承载平台

| 核心要素 | 说明 |
|----------|------|
| 账户 | 全量账户体系、资金流向、持仓关系 |
| 资产 | 资产类别、估值、风险敞口、关联穿透 |
| 客户信息 | 个人/机构/企业客户画像、分层标签、行为轨迹 |
| 员工行为 | 员工操作日志、权限轨迹、业绩关联 |
| 合同协议 | 产品合同、服务协议、监管报备文件 |
| 决策流程 | 业务审批节点、决策链路、历史决策记录 |
| 法规制度 | 内部制度、监管规则、合规知识库、处罚案例 |

**能力输出**：
- 关系网络：任意要素间的关联/穿透查询
- 预判式动作驱动：基于事件触发自动准备动作
- 统一语料：全公司数据语义打通
- 身份打通：员工账户与系统账户统一

### 1.2 企业技能蒸馏大模型

**定位**：业务知识→标准化模型的自动化蒸馏工厂

| 蒸馏能力 | 输出物 |
|----------|--------|
| 业务目标蒸馏 | 《业务目标清单》（经营什么、关键动作、衡量指标） |
| 标杆分析蒸馏 | 《标杆分析表》（找标杆、拆做法、评差距、定借鉴） |
| 数据关联蒸馏 | 《数据关联矩阵》（动作需要什么数据、在哪、怎么拿） |
| 模型定义蒸馏 | 产品模型 + 服务模型 + 动作模型 |
| 交叉验证/裁判验证 | 《交叉验证报告》+ 模型修正版 |

**核心规则内置**：
- 陶总五大反对（每步自动校验）
- 陶总八步可执行方法论（定目的→定角度→客观分类→提炼主维度→对比蒸馏→标准化建模→场景调用→监督迭代）
- 禁用词语表（自动替换/告警）

### 1.3 底座公共能力池

- **智能体通信协议**：MCP（Model Context Protocol）+ A2A（Agent-to-Agent）
- **记忆系统**：短期记忆（会话上下文）+ 长期记忆（知识库、历史经验）
- **工具调用白名单**：限定可调用的工具范围，高风险操作审批流
- **工程级提示词管理**：系统提示词（角色/约束/工具）+ 交互提示词（动态上下文）
- **统一身份认证**：员工身份与系统权限统一

## 第二层：标准化业务模型（第二圈）

**定位**：可被AI调用、可被员工执行的标准化技能原子库
**分类方式**：按模型类型（产品模型、服务模型、动作模型），而非按业务线

### 2.1 产品模型

**定义**：对金融产品/服务本身的标准化描述，包括产品结构、风险等级、适用人群、合规要求等

| 产品模型 | 核心维度 | 示例 |
|----------|----------|------|
| **资管产品模型** | 产品类型、策略、风险等级、费率结构、适投人群、合规备案 | 某混合型基金：策略（股债6:4）、R3风险、起投100万、适投C4以上客户 |
| **投行产品模型** | 发行类型、发行条件、承销方式、定价区间、合规要求、适用企业 | 某定增项目：定价基准、锁定期、募资用途、适用上市公司 |
| **债券产品模型** | 债券类型、发行主体、期限、利率结构、评级、适投机构 | 某公司债：3年期、AA+评级、固定利率、适投合格投资者 |
| **投顾产品模型** | 服务类型、配置策略、费率模式、服务内容、合规边界 | 某智能投顾：SAA模型、年费制、含调仓建议、人工确认触发 |
| **交易产品模型** | 交易品种、保证金比例、杠杆、风险敞口、合规限制 | 某两融标的：标的池、保证金、平仓线、集中度限制 |

**产品模型作用**：
- 为适当性匹配提供标准参照
- 为产品创设提供结构模板
- 为合规审查提供规则基准
- 为产品销售提供话术标准

### 2.2 服务模型

**定义**：对服务过程、服务标准、服务质量的标准化描述，包括服务流程、服务节点、验收标准等

| 服务模型 | 核心维度 | 示例 |
|----------|----------|------|
| **客户服务模型** | 服务分级、响应时效、服务内容、满意度标准、投诉处理 | 高净值客户：专属顾问、1小时响应、月度资产配置回顾 |
| **投顾服务模型** | 服务频次、沟通方式、建议范围、合规边界、留痕要求 | 投顾服务：季度调仓建议、APP推送、客户确认后执行 |
| **投后服务模型** | 报告频次、归因方式、风险提示、客户沟通、异常处理 | 投后服务：月度净值报告、季度归因分析、风险预警实时触达 |
| **承销服务模型** | 项目阶段、服务节点、交付标准、客户沟通、风险披露 | 承销服务：立项→辅导→申报→发行→持续督导，各阶段交付物 |
| **交易服务模型** | 执行标准、报价方式、风控节点、结算流程、异常处理 | 交易服务：询价→报价→确认→执行→结算，全链路留痕 |

**服务模型作用**：
- 为服务标准化提供参照
- 为客户体验一致性提供保障
- 为服务质量评估提供标准
- 为服务改进提供数据基准

### 2.3 动作模型

**定义**：对具体业务动作的标准化描述，包括动作触发条件、执行步骤、输出标准、异常处理、时限要求等

**通用动作模型结构（7事件）**：

```
事件名称：
  触发条件：
  执行步骤：
    1. 步骤一（责任人/工具/时限）
    2. 步骤二（责任人/工具/时限）
    ...
  输出标准：
  异常处理：
  时限要求：
  验收标准：
```

| 动作模型 | 适用场景 | 示例 |
|----------|----------|------|
| **客户开户动作** | 客户分层管理 | KYC→风险测评→适当性匹配→账户开立→服务初始化 |
| **资产配置动作** | 财富管理 | 读取画像→SAA模型→方案生成→客户确认→执行调仓→投后跟踪 |
| **产品创设动作** | 资产管理 | 需求洞察→策略回测→结构设计→合规审查→备案发行→销售准备 |
| **承揽立项动作** | 投资银行 | 行业扫描→企业快筛→条件匹配→项目立项→团队组建 |
| **尽调执行动作** | 投资银行 | 底稿清单→资料采集→数据验证→关联方穿透→报告生成 |
| **合规审查动作** | 全业务线 | 材料完整性→合规性校验→红线检测→风险提示→人工确认 |
| **交易执行动作** | 销售交易 | 信号生成→风控校验→报价确认→执行→结算→留痕 |

**动作模型作用**：
- 为智能体执行提供标准流程
- 为员工操作提供操作手册
- 为监督迭代提供数据基准
- 为业务培训提供教学素材

### 2.4 模型间关系

```
产品模型（有什么）
    ↓ 决定
服务模型（怎么服务）
    ↓ 支撑
动作模型（具体怎么做）
```

**示例：客户购买资管产品**
```
产品模型：某混合型基金（R3、起投100万、C4以上）
    ↓ 触发
服务模型：高净值客户投顾服务（1小时响应、月度回顾）
    ↓ 执行
动作模型：
  1. 客户画像读取（产品模型：适投人群匹配）
  2. 适当性匹配校验（产品模型：风险等级匹配）
  3. 配置方案生成（产品模型：产品结构融入方案）
  4. 客户确认（服务模型：沟通方式/合规边界）
  5. 下单执行（动作模型：交易执行标准）
  6. 投后跟踪（服务模型：投后服务标准）
```

### 2.5 已沉淀模型资产

| 模型类型 | 已沉淀资产 | 状态 |
|----------|----------|------|
| 产品模型 | 投行定增产品模型、债券发行产品模型 | 可用 |
| 服务模型 | 客户服务模型v3.0（个人/机构） | 可用 |
| 动作模型 | 投行承揽动作模型、债券发行动作模型 | 可用 |
| 分析模型 | 投行定增分析模型v5.0（5维度） | 可用 |
| 分析模型 | 债券发行分析模型v2.0（具体指标版） | 可用 |
| 分析模型 | 资管业务分析模型（5维度） | 可用 |
| 通用模型 | 交叉验证模型（裁判验证） | 可用 |

## 第三层：应用级智能体（助理）（第三圈）

**定位**：面向具体功能场景的智能体，按能力类型而非业务线划分，可跨业务线服务

### 3.1 客户分析助理

**角色定位**：客户理解与分层专家
**核心能力**：
- 客户画像构建（多源数据融合、动态标签、行为预测）
- 客户分层管理（高净值/普通、机构6类、企业）
- 需求识别（基于行为/持仓/交易/沟通的意图识别）
- 流失预警（特征监测、预警触发、挽留策略）
- 生命周期管理（新客户→成熟客户→高价值客户→流失风险）

**可调用模型**：
- 产品模型（适投人群匹配）
- 服务模型（服务分级匹配）
- 动作模型（客户开户动作、画像更新动作）

**服务对象**：
- 外部：全量客户（画像分析结果）
- 内部：财富顾问、资管产品经理、运营人员（客户洞察）

**三句话法合规**：
- 可以：内部客户画像分析、分层标签、需求洞察（纯内部使用）
- 必须确认：客户画像结果对外展示、精准营销推送（涉及客户隐私）
- 不：未经客户授权的数据采集、违规客户信息跨业务线共享

### 3.2 业务分析助理

**角色定位**：业务洞察与决策支持专家
**核心能力**：
- 业务数据分析（业务指标监控、趋势分析、异常检测）
- 行业/企业分析（行业景气度、企业质地、竞争格局）
- 项目评估（立项评估、可行性分析、风险识别）
- 市场窗口分析（发行时机、市场流动性、投资者情绪）
- 对标分析（与标杆企业/同业对比、差距分析）

**可调用模型**：
- 产品模型（产品结构分析）
- 服务模型（服务质量评估）
- 动作模型（承揽立项动作、项目评估动作）

**服务对象**：
- 外部：机构客户（行业研究报告）
- 内部：投行前台、研究员、业务支持中心（决策支持）

**三句话法合规**：
- 可以：内部数据分析、行业研究、项目评估（纯内部使用）
- 必须确认：面向客户的研究报告、投资建议类输出（涉及客户决策）
- 不：预测股价/市场走势、无资质投资建议、承诺保本保收益

### 3.3 产品和服务方案创设助理

**角色定位**：产品设计与服务方案生成专家
**核心能力**：
- 产品结构设计（产品要素组合、风险等级匹配、合规边界校验）
- 服务方案生成（服务分级、服务内容、服务标准、交付物）
- 配置方案生成（SAA/TAA模型、组合构建、压力测试）
- 合同/协议生成（合同模板匹配、条款生成、合规审查）
- 方案优化（基于反馈迭代、标杆对比、数据驱动改进）

**可调用模型**：
- 产品模型（产品要素库）
- 服务模型（服务标准库）
- 动作模型（产品创设动作、方案生成动作）

**服务对象**：
- 外部：客户（配置方案、产品说明书）
- 内部：资管产品经理、财富顾问、投行前台（创设辅助）

**三句话法合规**：
- 可以：内部方案设计、产品结构设计、合同初稿（纯内部使用）
- 必须确认：面向客户的配置方案、产品推荐、合同签署（涉及客户资金/合规）
- 不：承诺保本保收益、承诺发行成功、无资质产品设计

### 3.4 账户服务助理

**角色定位**：账户管理与业务执行专家
**核心能力**：
- 账户管理（开户、销户、信息变更、权限管理）
- 交易执行（指令接收、风控校验、执行确认、结算跟踪）
- 资金清算（资金划转、清算对账、异常处理）
- 业务办理（业务申请、材料审核、进度跟踪、结果通知）
- 运营自动化（报表生成、数据统计、日常运营、通知推送）

**可调用模型**：
- 产品模型（产品账户关联）
- 服务模型（服务执行标准）
- 动作模型（交易执行动作、账户管理动作）

**服务对象**：
- 外部：客户（账户服务、交易确认）
- 内部：运营人员、交易员、业务支持中心（业务执行）

**三句话法合规**：
- 可以：内部运营自动化、报表生成、数据整理（纯内部使用）
- 必须确认：客户账户变更、交易执行、资金划转（涉及客户资金）
- 不：代客下单交易、违规资金操作、客户身份未核实就开户

### 3.5 交叉验证助理

**角色定位**：质量检验与独立裁判
**核心能力**：
- 内部自洽验证（逻辑一致性、数据勾稽、规则符合性）
- 标杆对比验证（与行业标准、标杆案例、历史数据对比）
- 可执行性模拟（流程模拟、异常测试、边界验证）
- 独立裁判挑刺（第三视角审视、假设质疑、风险点挖掘）
- 合规红线扫描（规则库匹配、红线检测、风险提示）

**可调用模型**：
- 产品模型（产品合规性校验）
- 服务模型（服务标准符合性）
- 动作模型（动作合规性校验）
- 交叉验证模型（裁判验证专用）

**服务对象**：
- 内部：合规审查员、内核委员、业务支持中心（质量把关）
- 外部：监管机构（可审计性、可追溯性）

**三句话法合规**：
- 可以：内部验证、质量检查、合规扫描（纯内部使用）
- 必须确认：验证结论对外使用、合规意见出具（涉及监管/客户）
- 不：绕过验证直接发布、伪造验证结果、故意忽略红线

### 3.6 五个助理的协作关系

```
客户分析助理（理解客户）
    ↓ 输入客户画像
业务分析助理（分析业务）
    ↓ 输入业务洞察
产品和服务方案创设助理（设计方案）
    ↓ 输出方案
账户服务助理（执行服务）
    ↓ 执行结果
交叉验证助理（验证质量）
    ↓ 反馈迭代
产品和服务方案创设助理（优化方案）
```

**典型协作链路**：

**链路1：高净值客户资产配置**
```
客户分析助理：读取客户画像 → 风险等级 → 需求标签
    ↓
业务分析助理：市场分析 → 行业趋势 → 产品评估
    ↓
产品和服务方案创设助理：SAA模型 → 配置方案 → 压力测试
```

### 4.3 组织者

**角色定位**：业务支持中心（中后台）——统一调度者、能力编排者、质量监督者

**核心职责**：
- 任务编排：接收业务需求，分解为助理任务链，分配给各助理执行
- 能力调度：根据业务场景，选择合适的产品模型、服务模型、动作模型
- 质量监督：通过交叉验证助理，对所有输出进行质量把控
- 迭代优化：收集业务反馈，驱动企业技能蒸馏大模型迭代模型
- 异常处理：处理助理无法处理的异常，升级人工决策

**工作模式**：
```
业务需求（前台/客户）→ 组织者（业务支持中心）
    ↓ 任务分解
    ├─→ 客户分析助理（理解客户）
    ├─→ 业务分析助理（分析业务）
    ├─→ 产品和服务方案创设助理（设计方案）
    ├─→ 交叉验证助理（验证质量）
    └─→ 账户服务助理（执行落地）
    ↓ 结果汇总
    输出 → 前台/客户
    ↓ 反馈收集
    驱动蒸馏大模型迭代模型
```

**组织者与其他角色的关系**：
- 对前台：不是"审批者"，而是"赋能者"——提供标准化能力，让前台直接调用
- 对客户：不是"直接接触者"，而是"能力调度者"——通过助理间接服务客户
- 对助理：不是"操作者"，而是"编排者"——设计任务流，监督执行质量
