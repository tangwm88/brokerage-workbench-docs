## 战略更新：智能体建设进入新阶段

**时间**：09:44  
**来源**：用户直接指令

### 新阶段核心目标
从"能不能建"转向"好不好用"，确保建设的智能体都是：
- **好用** — 用户体验顺畅，前端3-4步达成业务
- **易用** — 上手简单、操作直观、无需培训即可调用
- **管用** — 真正解决业务痛点，量化价值可感知

### 现阶段重点任务
**任务一：各智能体与多角色员工工作台的融合**  
将各业务线智能体接入多角色员工工作台，让不同角色的员工能在统一界面调用所需能力。"好用"和"易用"的关键承载平台。

**任务二：各智能体业务模型的落实**  
将方案设计阶段定义的各智能体角色能力拆解为具体可落地的业务模型（Skills），形成每个智能体包含的能力模型清单。

### 新增核心工作：业务模型建设（Skills设计与建设落实）

这是比之前的"智能体方案设计"更下沉一层的工作——从"业务目标+角色定义"下沉到"具体能力模型清单"。

#### 模型设计输出物
| 要素 | 说明 |
|------|------|
| 模型能力名称 | 用户视角能看懂的技能单元 |
| 主要维度 | 最关键、最有价值、非传统的维度 |
| 下级子模型 | 能力拆解后的子技能 |
| 模型说明 | 能力边界、使用场景、输出标准 |

#### 模型设计原则
1. **对应语料** — 每个模型有明确的语料支撑
2. **提示词** — 每个模型有配套的提示词工程
3. **模型规则** — 每个模型有运行规则（输入、处理、输出、异常）

#### 颗粒度标准
> **以用户视角能看得懂的技能单元为标准**

这意味着：
- 不能太粗（如"客户服务"这种大筐不行）
- 不能太细（如"字符串拼接"这种技术细节不行）
- 要像业务人员描述自己工作那样自然

#### 命名与维度要求
- **名称**：通俗易懂，不用技术黑话
- **维度**：取最关键、最有价值、非传统的视角，避免"通用能力+业务标签"的敷衍做法

### 与现有工作的关系

```
已有工作（方案设计层）        新增工作（模型建设层）
├─ 业务目标定义          →    ├─ 能力模型清单
├─ 角色定义              →    ├─ 模型能力名称
├─ 底座调用设计          →    ├─ 主要维度设计
├─ 动作标准              →    ├─ 下级子模型拆分
├─ 提示词规范            →    ├─ 模型说明（语料/提示词/规则）
└─ 评审检查清单          →    └─ 模型颗粒度验证
```

### 下一步行动
